# RoadShare submission

- Working prototype: https://roadshare-app.onrender.com/
- Public repository: https://github.com/sarayu-uu/custody_board

## 300-word summary

RoadShare follows the machine from request to return so responsibility is always visible. A Crew Chief checks the board, selects an open period, states the work and location, and creates a booking. The system rejects past times, overlapping reservations, and any request for maintenance-locked equipment. At pickup or transfer, the current town records fuel, hour-meter reading, checklist results, condition notes, and photos; custody changes only after the receiving crew confirms acceptance. The hour meter cannot decrease, and completed handoffs remain in history. If a defect is found, a Crew Chief may report it with proof, while a Fleet Mechanic may report and lock it directly. A serious defect stops reservations, emergencies, and handoffs and marks future work at risk. The mechanic records diagnosis and repair, but the machine stays unavailable until the Equipment Admin, representing the Town Supervisor, clears it. For storm or flood work, a Crew Chief submits a reasoned emergency request. The Admin reviews timing, impact, and displaced work. Approval creates emergency use, preserves the booking as PREEMPTED, records why, and lets the affected town reschedule. Every request, decision, condition record, custody transfer, repair, clearance, and reschedule adds an append-only audit event. Offline entries wait in Needs Review instead of appearing falsely confirmed.

At 10× usage, browser-local state would produce conflicting schedules across phones, reordered offline submissions, duplicated approvals, growing evidence storage, and heavier administrative workload. PostgreSQL should become authoritative, using transactional time-range constraints, row versions, idempotency keys, and server timestamps. FastAPI should enforce authenticated, town-scoped roles; encrypted object storage should hold evidence; and server-owned append-only audit records should support disputes. WebSockets should broadcast booking, custody, emergency, and maintenance changes, while a queue handles notifications and retries. The organization would also need emergency priority policy, approval deadlines, repair ownership, evidence retention, monitoring, backups, and an explicit conflict-resolution process.
